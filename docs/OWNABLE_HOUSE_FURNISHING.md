# Fixed furnishings for reviewed, unowned player-ownable houses

The chosen model is **immutable, server-owned fixtures that stay with the house**.
They are not gifts, trade goods, tenant inventory or replenishable loot. New
activation requires a reviewed house that is unowned in both the loaded game and
an atomic database ownership check. Already-owned homes without activation history
are never furnished. Production approvals remain empty; zero houses are activated
by shipping this code.

## Lifecycle contract

| Event | Fixtures | Player property / native behavior |
| --- | --- | --- |
| First reviewed unowned activation | Commit exact plan, then place inert fixtures only on clear approved tiles | Existing objects never moved, replaced or removed; occupied target blocks entire activation |
| Purchase | Same physical fixed objects remain | Native purchase price, premium checks and ownership setter unchanged |
| Sale / deed transfer | Stay with house; do not go to seller's depot | Native transfer sends ordinary goods to seller's depot and handles access/bed state |
| Leave / rent repossession / owner becomes zero | Stay fixed; activation record retained | Native ownership cleanup and ordinary property handling unchanged |
| Repurchase, including repeated owner-zero cycles | Same plan; no additional grant | No loot or movable furniture can be generated by a purchase cycle |
| Save | Inert fixtures excluded by native stationary-item save rules | Ordinary items/containers and nested contents use unchanged native `tile_store` serialization |
| Restart | Restore committed fixtures **after ownership metadata, before saved items** | Native saved containers/objects then load around the same fixed layout |
| Manifest entry removed or edited after activation | Stored original plan remains authoritative | An ordinary manifest edit cannot silently replace a tenant's layout |
| Reset / reload request | Reconstruction is idempotent, never a wipe or restock | No deletion of player goods, plan purge, tenant-inventory reset or reward reset API exists |
| Feature/master disabled at restart | No overlay reconstruction; historical map geometry returns | Native house ownership and saved property still load normally; activation history is retained |
| Source map/house identity or item safety changes | Hold restoration with diagnostics | No forced insertion, relocation or deletion of saved player contents |

Changing or retiring a committed layout requires a separately reviewed migration,
not deleting ledger rows or editing a profile while a tenant owns the house. Staff
can always alter the world through privileged tools; ordinary players cannot pick
up, rotate, destroy, sell, trade or turn these inert types into containers. A GM
removing a fixture is not a supported tenant furnishing operation: the stored
plan reconstructs on the next valid cold start. There is no live destructive
"reset house" command and no periodic generation timer.

## Why this model

Removing everything at purchase would risk mixed/player contents and would need
to interpose on money, house transfer and save transactions. Giving movable
furniture would turn unowned/purchased/reset cycles into a sale source. Saving
new stationary containers without source-map counterparts can lose their contents
on native reload. This model instead mirrors native fixed map furniture through
an isolated, durable overlay: immutable non-container types, reconstructed before
native contents. No ownership API or financial transaction is rewritten.

`House::setOwner`, `House::executeTransfer`, `House::transferToDepot` and rent
repossession keep their original implementation. Native transfer ignores the
non-pickupable, non-container fixtures. Native `saveTile` omits these inert types;
there is no second serialized copy to restore from `tile_store`. A player bag on a
table is still saved as a player bag, with its nested contents, and loads after
that table has been reconstructed. Unowned house contents remain natively saved.

## Controls and approval schema

```lua
easyModeEnabled = true
easyModeHouseFurnishing = true
easyModeOwnableHouseFurnishing = true -- NEW; generic default is false
```

All are startup-only. Ownable-house activation/restoration requires all three.
The existing `easyModeHouseLoot` flag never authorizes loot in ownable houses.
No Action IDs, player storage keys or client modifications are added. Existing
public-interior/one-time-loose-loot behavior is unchanged.

Use the existing version-1 `data/zedas/houses.xml`, extended with:

```xml
<interior id="reviewed-house-example" profile="poor-residence"
          classification="reviewed-unowned-house" review="ACTUAL REVIEW RECORD REQUIRED"
          houseId="REPLACE_WITH_VERIFIED_ID" houseSignature="EXACT_SIGNATURE"
          x="ANCHOR_X" y="ANCHOR_Y" z="FLOOR" ground="GROUND_ID">
  <place role="table" x="FIXTURE_X" y="FIXTURE_Y" z="FLOOR" ground="GROUND_ID" />
</interior>
```

This is schematic, intentionally not a production-ready approval. Root map SHA-1,
all existing bounds and exact-role/item rules still apply. Ownable placements must
select **only fixture roles**, belong to the exact HouseTile ID, match bare ground,
and pass movement/action/item-state checks. There may be only one plan per house
in a manifest. Adjacent actors and tiles of a different house block initial placement. House signature binds the
native house ID/name, entry coordinates and complete sorted tile footprint; it is
independent of owner, rent payment state and player contents. The identity helper
`python3 tools/audit/house_fixture_signature.py --house-id ID` uses the checked
source inventory and prints identity metadata only, **never approval or live
ownership**. House/position/safety review is still mandatory.

The five shipped profiles remain vocabulary only. Choosing an unused fixture
role from a profile that also defines food does not grant its food. Selecting a
loot role in an ownable plan rejects the manifest. Beds, doors, depots, functional
containers, movable/destructible/transforming/charged/scripted furnishings remain
unsupported. No house is inferred safe from owner zero, house name, rent or ID.

## Durable activation and ordering

Explicit additive migration **004_house_fixtures.sql** creates
`zedas_house_fixtures`: primary key `house_id`, plan hash, exact sealed XML plan and
activation time, with a restrictive reference to `houses.id`. Apply it manually
before enabling this option. Migration 003 is not needed for fixture-only houses.
The new flag off means no fixture-ledger connection or restoration work; ordinary
Classic operation needs no migration.

The bounded, isolated no-reconnect DB session uses autocommit and InnoDB. Initial
activation uses a single `INSERT ... SELECT ... FROM houses WHERE owner=0` and
requires exactly one inserted row. This closes the stale-memory ownership race.
The immutable primary key stops a second activation, profile replacement or
purchase-cycle replenishment. No feature path updates/deletes/replaces this plan.
An uncertain commit places nothing in that attempt; the next startup can recover
a committed plan. Unlike recoverable loot, fixtures have no movable value, so
reconstruction after a crash does not duplicate an economic item.

The persisted snapshot contains only the approved inert definitions and positions,
not player items. Restoration verifies the snapshot hash, current whole-map hash,
current house signature, exact tile membership/ground and current native item
safety. `Map::loadMap` calls it immediately after `loadHouseInfo` and before
`loadHouseItems`. New activation remains after full normal map/item/actor startup,
so pre-existing contents are visible and block new insertion. Existing activated
owned houses are reconstructed from their stored snapshot, independently of the
current approval file. Partial placement failure never triggers compensating
removal of other objects; the sealed plan remains recoverable on a later clean
restart. Diagnostics report restored/rejected plans and any ledger unavailability.

This does not redesign the historical multi-transaction player/house save system.
It avoids adding another movable-item copy. Keep activation records with DB
backups. Dropping house rows is blocked by the plan FK until an operator reviews
retirement; ordinary purchase/transfer/repossess paths do not delete house rows.
Do not redefine fixture item IDs into mutable/container types or restore mixed-age
DB snapshots as a furnishing reset.

## Validation and original-client checks

Automated lifecycle tests use a synthetic ownable HouseTile house, real native
ownership/deed/depot/save/load APIs, a disposable DB and separate processes:
occupied and already-owned rejection; stale-memory owner race; one activation;
purchase retaining exact objects; player bag/nested coins surviving save/restart;
fixtures absent from native item serialization; actual deed transfer preserving
fixtures and delivering goods to the seller's depot; vacating/repossessing and
repurchase without restock; stored-plan restoration with no current manifest;
identity mismatch and disabled/master-disabled behavior. General house overlay,
Classic, broker, loot, full normal/sanitizer and both Lua suites remain required.

1. Keep the production file empty. With the new flag off, verify existing houses,
   doors/beds, belongings, transfers and saves behave as before.
2. In a separate test DB/map, approve a reviewed synthetic unowned house with
   exact identity/clear tiles. Apply migration 004 there. Enable the three flags.
   Verify fixed appearance, ordinary immobility and paths in original 7.72.
3. Put an unrelated item on a target before activation: expect rejection with
   every existing object intact. An owned house with no activation must also reject.
4. Activate while vacant, buy normally, place a bag with nested contents on a table,
   save/restart. Verify one table/carpet and the exact bag contents. Repeat restart.
5. Transfer/sell using the native deed flow. Fixed objects remain in the house;
   ordinary goods follow native seller-depot behavior. Leave/repossess and rebuy:
   expect no second plan, loose loot, movable fixture or saleable furnishing.
6. Edit/remove the current approval entry after activation: cold restart must keep
   the stored original layout. Changing map/house identity instead must hold the
   stale plan, with no deletion or forced relocation of belongings.
7. Disable the option/master and restart: only the original map layout and normal
   saved contents load. Re-enable and restart: the same valid fixed plan returns.
8. Restore the empty production approvals and disabled flags after testing. Do not
   purge plan rows or use ownership cycles as a reset. Production promotion still
   requires explicit location review; this pass approves zero real houses.
